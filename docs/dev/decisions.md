# Decisions

Durable product and architecture decisions. Design-level decisions D1 to D14 are tabulated in `docs/planning/03-architecture-design.md` section 11; this log records decisions made after that document, and repo-level ones.

| Date | Decision | Why | Consequence |
|---|---|---|---|
| 2026-10-14 | Implementation language is Go | Team's chosen language | Graphiti and Hindsight are design sources only; no Python dependencies |
| 2026-10-14 | One module, three binaries: `froodbase-mcp` (local), `froodbase-api`, `froodbase-dreamer` | Shared domain rules; local ingestion preview; simpler client sign-in | Per-machine binary needs a release and update path |
| 2026-10-14 | Product renamed from "The Brain" to Froodbase; repository created at `~/src/Froodbase` | Product naming | All documents and binary names use Froodbase |
| 2026-10-14 | Foundation follows the shared default project foundation (facts, docs/dev, changelog, feature-branch workflow) | Consistency with other repositories | Policies live in `.agents/facts/` |
| 2026-10-14 | Build a local MVP of the brain before any cloud infrastructure; Gate 0 of the implementation plan is taken as build | Judge the knowledge model, temporal rules, disputes, retrieval and dreamer jobs on one computer before paying to operate them | Scope in `docs/planning/07-local-mvp.md`; implementation plan phases 1 and 2 are localised, phase 0 organisational work waits for the cloud move |
| 2026-10-14 | Local runtime is Docker Compose: PostgreSQL 16 with pgvector, pg_trgm and btree_gist, `froodbase-api` and `froodbase-dreamer` as containers; `froodbase-mcp` runs on the host as a stdio server in Claude Code | Same images as the cloud; the three-binary split is kept so the move is a hosting change | `froodbase-mcp` never connects to PostgreSQL; `froodbase-api` is the only writer |
| 2026-10-14 | Authentication for the MVP is HTTP basic auth against a static user list, behind the `internal/authz` authorisation-context interface | No Entra tenant locally; the rest of the service must only see (area, role) grants | Entra becomes a second implementation of the same interface; no basic-auth type may appear in the interface signature |
| 2026-10-14 | Migrations use goose, versioned and forward-only; locally run by a `make` target, in the cloud only from the pipeline | Widely used, SQL-first, fits sqlc | TR-92 unchanged for cloud environments |
| 2026-10-14 | Integration tests use Testcontainers for Go with a disposable PostgreSQL, tagged `integration` | The test gate must not depend on a running Compose stack | Docker is a prerequisite for the integration suite; the unit gate stays Docker-free |
| 2026-10-14 | Flashheart ticket key is `FRB` | Short and recognisable | Ticket ids are `FRB-n`; PR titles start with the id |
| 2026-10-14 | Repository hosted at `github.com/rztaylor/Froodbase`; module path kept lowercase `github.com/rztaylor/froodbase` | Owner's choice of home; Go module paths are conventionally lowercase and GitHub resolves the name case-insensitively | Foundation landed as the first commit on `main`; all later changes arrive by pull request |
| 2026-10-14 | Work is organised as vertical slices, each advancing `froodbase-api`, `froodbase-mcp` and `froodbase-dreamer` together | The owner wants to see all three improve in lockstep, not a dark dreamer until the end | One workstream per slice on the board; every slice ends runnable in Claude with its own integration tests |
| 2026-10-14 | Server images are built from one root `Dockerfile` parameterised by `BINARY`: multi-stage, static Go build, Alpine runtime as a non-root user | One build definition for `froodbase-api` and `froodbase-dreamer`; Alpine provides `wget` for the Compose health check without adding tooling to the binaries | The same `Dockerfile` serves the cloud images; the local database password is generated into `.env` by `make up`, never committed |
| 2026-10-15 | Evidence vocabulary: source kinds `repository`, `ticket`, `telemetry_query`, `document`, `report_revision`; access classes `restricted` < `area` < `organisation`; shared sources must be `https` URLs on a non-loopback host, report revisions `froodbase://report-revisions/<id>`; every citation except a report revision names its source revision | TR-24 and TR-61 name the kinds and require allowed patterns and an access ordering but do not spell them; PR-10 requires the revision | Fixed in `internal/domain`; the schema (FRB-9) stores these strings and a CHECK constraint can mirror them. Adding a kind or class is a domain change with tests first |
| 2026-10-16 | Ingestion normally extracts evidenced records from living sources; retaining an original report or document is an explicit option only when its benefit and access class are shown | Repositories, Confluence pages and reports can change, and preserving their entire bodies is not needed for most reusable claims | Source identity, revision and precise locator stay with extracted records; a separately approved retained copy is not an independent evidence root |
| 2026-10-16 | Authorised reviewers can inspect all contributed claims and decisions at any time and flag an individual claim for reconsideration | A due-for-review queue and operational audit events alone do not show the full knowledge history or let a human challenge an accepted deduction | Contribution, claim and revision records form a permission-scoped review history; flags append reasons without changing acceptance or validity until review |
| 2026-10-16 | Adapt OpenBrain's capture, import-lineage, recall-feedback and evidence-quality practices through Froodbase's existing services | The [OB1 assessment](../planning/08-reuse-research-openbrain.md) found useful workflow detail beyond the Graphiti/Hindsight knowledge-design work | The product and technical requirements specify these additions; implementation follows the existing local-MVP and pilot sequence without adopting OB1 as a runtime |
| 2026-10-16 | Separate a claim's epistemic kind, evidential support and lifecycle disposition; allow versioned area policies to accept independently supported AI inferences automatically | Continuous human approval would bottleneck ingestion and learning. New independent proof should strengthen a claim while fluency, duplicated sources and model confidence confer no authority | Every generated inference begins proposed. Support reassessment and policy decisions append evidence roots, input revisions and rationale; qualifying inferences may be accepted without changing their inferred kind. Ambiguous sufficiency and disputes go to human review, and all claims remain inspectable and flaggable (FRB-45) |
| 2026-10-16 | Certainty is an earned support score and the lifecycle has no proposed or accepted state: active, disputed, superseded, retracted. Support events are distinct evidence roots, verifications, evidenced use outcomes (`report_outcome`), a capped quiet-use credit, and the negative events contradiction, failed outcome, source change, flag and retracted dependency. Retrieval, repetition and model confidence add nothing. Areas set per-kind thresholds that drive the insufficient-evidence flag. This supersedes the acceptance-policy decision above and FRB-45's sufficiency predicates | Nobody can write an independently checkable sufficiency predicate for a causal inference, so a policy gate collapsed back into human review and inferred knowledge stopped at "proposed". Applying a lesson and observing with evidence that it worked is a genuine new observation in a new scope, which is what verification means; reading it is not | Planning documents, facts and board tickets rewritten (FRB-46). Schema: `support_event` and `support_config` replace the planned support assessment and acceptance policy tables; `review_claim` and `report_outcome` replace `review_contribution` and `verify_record`; `propose_contribution` is renamed `contribute`. Reviewers correct and resolve; they approve nothing |
| 2026-10-16 | Reports, conversations and transcripts are never an input to Froodbase, and no document body or copy is ever stored. Agents contribute individual evidenced findings as they work and list the identifiers in the report. The `ingest_report` tool, the local preview in `froodbase-mcp`, source-copy retention and the `report_revision` source kind are removed from the design; this supersedes the source-retention decision above | The pitch's "reports remain local" rule was about the whole document and the conversation inside it, not about a per-finding approval step; the preview-and-approve path had grown into the main path and recreated the bottleneck, and a report store is a non-goal | `internal/domain` drops the `report_revision` source kind in a follow-up code ticket; importing an old report is a skill that reads the file locally and calls `contribute` |
