| 2026-10-15 | Evidence vocabulary: source kinds `repository`, `ticket`, `telemetry_query`, `document` (`report_revision` was included and removed on 2026-10-20, see below); access classes `restricted` < `area` < `organisation`; shared sources must be `https` URLs on a non-loopback host, report revisions `froodbase://report-revisions/<id>`; every citation except a report revision names its source revision | TR-24 and TR-61 name the kinds and require allowed patterns and an access ordering but do not spell them; PR-10 requires the revision | Fixed in `internal/domain`; the schema (FRB-9) stores these strings and a CHECK constraint can mirror them. | 2026-10-16 | Ingestion normally extracts evidenced records from living sources; retaining an original report or document is an explicit option only when its benefit and access class are shown | Repositories, Confluence pages and reports can change, and preserving their entire bodies is not needed for most reusable claims | Source identity, revision and precise locator stay with extracted records; a separately approved retained copy is not an independent evidence root |
| 2026-10-16 | Authorised reviewers can inspect all contributed claims and decisions at any time and flag an individual claim for reconsideration | A due-for-review queue and operational audit events alone do not show the full knowledge history or let a human challenge an accepted deduction | Contribution, claim and revision records form a permission-scoped review history; flags append reasons without changing acceptance or validity until review |
| 2026-10-16 | Adapt OpenBrain's capture, import-lineage, recall-feedback and evidence-quality practices through Froodbase's existing services | The [OB1 assessment](../planning/08-reuse-research-openbrain.md) found useful workflow detail beyond the Graphiti/Hindsight knowledge-design work | The product and technical requirements specify these additions; implementation follows the existing local-MVP and pilot sequence without adopting OB1 as a runtime |
| 2026-10-16 | Separate a claim's epistemic kind, evidential support and lifecycle disposition; allow versioned area policies to accept independently supported AI inferences automatically | Continuous human approval would bottleneck ingestion and learning. New independent proof should strengthen a claim while fluency, duplicated sources and model confidence confer no authority | Every generated inference begins proposed. Support reassessment and policy decisions append evidence roots, input revisions and rationale; qualifying inferences may be accepted without changing their inferred kind. Ambiguous sufficiency and disputes go to human review, and all claims remain inspectable and flaggable (FRB-45) |
| 2026-10-16 | Certainty is an earned support score and the lifecycle has no proposed or accepted state: active, disputed, superseded, retracted. Support events are distinct evidence roots, verifications, evidenced use outcomes (`report_outcome`), a capped quiet-use credit, and the negative events contradiction, failed outcome, source change, flag and retracted dependency. Retrieval, repetition and model confidence add nothing. Areas set per-kind thresholds that drive the insufficient-evidence flag. This supersedes the acceptance-policy decision above and FRB-45's sufficiency predicates | Nobody can write an independently checkable sufficiency predicate for a causal inference, so a policy gate collapsed back into human review and inferred knowledge stopped at "proposed". Applying a lesson and observing with evidence that it worked is a genuine new observation in a new scope, which is what verification means; reading it is not | Planning documents, facts and board tickets rewritten (FRB-46). Schema: `support_event` and `support_config` replace the planned support assessment and acceptance policy tables; `review_claim` and `report_outcome` replace `review_contribution` and `verify_record`; `propose_contribution` is renamed `contribute`. Reviewers correct and resolve; they approve nothing |
| 2026-10-16 | Reports, conversations and transcripts are never an input to Froodbase, and no document body or copy is ever stored. Agents contribute individual evidenced findings as they work and list the identifiers in the report. The `ingest_report` tool, the local preview in `froodbase-mcp`, source-copy retention and the `report_revision` source kind are removed from the design; this supersedes the source-retention decision above | The pitch's "reports remain local" rule was about the whole document and the conversation inside it, not about a per-finding approval step; the preview-and-approve path had grown into the main path and recreated the bottleneck, and a report store is a non-goal | `internal/domain` drops the `report_revision` source kind in a follow-up code ticket; importing an old report is a skill that reads the file locally and calls `contribute` |
| 2026-10-20 | The `report_revision` source kind and the `froodbase://` URI scheme are removed from `internal/domain`; every evidence record cites an https source and names its revision | Reports are never an input and no copy is ever stored (decision of 2026-10-16), so evidence held inside Froodbase can never exist | Four source kinds; the URI validator has one rule; a future internal store of sources needs a new decision, not a revival |
| 2026-10-20 | Row-level security is keyed on `app.caller_areas`, a comma-separated list of area ids set per transaction with `set_config(..., true)` by the service, which connects as the non-owning role `froodbase_app`; the migrating owner role is the only one the policies do not apply to. Grant keys are mapped to ids by the `SECURITY DEFINER` function `app_area_ids` before the variable is set | TR-71 asks for a session variable and a service role that cannot bypass the policies; comparing ids directly keeps every policy a cheap array test with no join, and an unset variable fails closed | Every record table carries `area_id`, including the join tables; the api sets the variable from the authorisation context; jobs that must read across areas (the dreamer) need their own decision, for now they see no records |
| 2026-10-20 | Revisions snapshot content only; support is never part of a snapshot, and linking further evidence to a claim changes its score and appends support and audit events without a new revision | The score is a projection of the append-only support events (TR-29), so the events are its history; a content revision for every support change would double the history and invite reading support from a snapshot | `get_history` shows content revisions; support history is read from `support_event`; `RecomputeSupportScore` must always equal the stored score |
| 2026-10-20 | Evidence is immutable and unique per (area, source URI, revision, locator); the service default support configuration is the row with a null area and version `service-1`, and an area's own versions are append-only rows | A source cited twice is one root (PR-12); an edited configuration would silently change what stored scores mean (TR-43) | Contributing a known source again links the existing record (`ErrDuplicateEvidence` otherwise); scores name the version they were computed under and recompute under it |
| 2026-10-20 | sqlc generates the store's queries; it runs through `go run` at a pinned version and the output is committed under `internal/store/gen`, checked by `make sqlc-check` in CI | Typed queries without a runtime dependency (the generated code imports only pgx) and without a tool to install | Changing a query or a migration means regenerating; the generated package is exempt from the `doc.go` rule |
| 2026-10-20 | The tool contract (inputs and outputs of every tool) lives in `internal/wire`, imported by the tool definitions, the API engines and the forwarding client | Both binaries must agree on the shapes without `froodbase-mcp` importing the store | A new tool adds its types to `wire`, its definition to `mcpserver`, its handler to `apihandlers` and its forwarder to `client` |
| 2026-10-20 | In the local MVP, knowledge areas are created at `froodbase-api` start-up for every area key the users file grants, named after the key; idempotency keys are stored per human caller with a hash of the request and the stored result, in the same transaction as the write | No admin tool exists yet and grants already name the areas; a retry must find the whole result or nothing (TR-15) | The cloud move adds an admin tool for areas; a key reused with different content is refused |
| 2026-10-20 | A dreamer job acts within the area it was enqueued for: its store caller holds that area id only, so row-level security applies to jobs as to people. Projection bookkeeping (`index_state`) holds identifiers and revisions only and is not area-scoped; staleness across areas is counted by a `SECURITY DEFINER` function that returns counts | Jobs must not become a path around the policies, and the dreamer must report staleness across every area without reading content | A job that needs several areas is enqueued once per area; `index_state` is never joined into tool results |
| 2026-10-20 | Replan the local MVP: slice 1b (deductions as inferences and decisions with derivation links, evidence from commands and from named people, plain-language contribution through a repository skill, document extraction, root propagation to deductions) before slices 2 and 3; slice 3b (import the system-map-discovery architecture references, regenerate them as knowledge views readable from Claude, and prove coverage) after slice 3 and before slice 5; the exit gate includes taking over from those references | Using slice 1 showed a strict fact store: no way to share a deduction, only web citations, every field supplied by the person, and nothing that could replace the Markdown references agents rely on. The product rules already allow first-class deductions with earned support; the plan had scheduled them late and deferred the views to phase 6 | Board workstreams slice-1b and slice-3b; slice 2 and slice 3 wait for 1b, slice 5 waits for 3b; derivation links leave slice 4; phase 3 importing and phase 6 views start in the MVP for this one corpus |
| 2026-10-20 | Deductions are assertions of kind decision or inference linked to their sources by an append-only `derivation` row in the same area (composite foreign keys enforce the area). A deduction's initial support is one `root_added` event per distinct root of its sources' `root_added` events plus its own citations, so it inherits transitively and a shared root counts once; inherited events name their sources as the rationale. An observation is never derived, and a decision or inference needs evidence, sources or both. `contribute` takes `assertions` with a `kind`; `observations` stays as the observation-only form | Agents must be able to record what they concluded, not only what they saw, without the conclusion earning support its evidence does not give it (PR-12, PR-13, PR-42) | Derivations are written only with a new record, so cycles can only arise within one call and are refused there; reassessing a deduction when a source's support changes is FRB-52; the `observations` field can be retired once callers use `assertions` |
| 2026-10-21 | Evidence must be checkable by its intended audience rather than openable (PR-11, TR-24, TR-61). Two source kinds join the four https kinds: `command` cites what a command or query observed (`azure:///<ARM id>`, `k8s://<cluster>/[<namespace>/]<kind>/<name>`, `sql://<server>/<database>`, `host://<name>`), the command in the locator and the run time as `observed_at`, which is also the default revision, so each run is its own root; `statement` cites `person://<user id>` of the human caller only, what was said as the excerpt and when, keyed on the excerpt as well so two things said at once are two records. One person's statements count as one root per claim. `SupportConfig` gains `root_weight_by_source_kind` (each in [0, 1]; a `root_added` event earns its event weight times its root's weight, recorded on the event as `source_kind`): every observed kind 1, statement 0.5. `service-1` keeps its version, extended with the new field. Any URI, locator or excerpt that looks like a credential is refused with the kind of secret, never the value | Facts found with az, kubectl or SQL, and knowledge people hold, were excluded and pushed into private notes; Froodbase is shared memory with provenance, so it records them, labelled and weighted, rather than refusing them. Repeating oneself is repetition, which earns nothing (PR-15). No existing score changes: every root stored before had an observed kind, weighed 1 | Migration 00006 widens the source kind check, splits the evidence uniqueness index for statements, adds and backfills `support_event.source_kind` and adds the root weights to every stored configuration. A new source kind needs its weight in every configuration. The secret patterns are a guard, not a scanner: agents still scrub output before contributing |
| 2026-10-21 | Strengthening propagation (TR-44): when a record with dependants gains a root, the writer enqueues `reconsider_derived` (unique per record while waiting or running) in the same transaction, from `addRoots`, so every root-adding path enqueues it. The job walks the derivation links transitively (`domain.Dependants`: breadth-first, sources first, each record once, cycles broken at the first record reached) and brings each dependant up to date with its direct sources' current roots, rather than replaying the change that enqueued it; its `root_added` events carry `job_name` and no user, and it writes no revision or audit event. Concurrency: `addRoots` locks the claim for update; the job holds the changed record for share and completes itself (`river.JobCompleteTx`) in the walk's transaction; a contribution deriving from an existing record holds the source for share | Collapsed jobs must lose nothing, and River's uniqueness counts a running job as waiting, so a root added while the walk ran could otherwise be folded into a job that never sees it; reading current state makes the job idempotent and lets the weakening events (FRB-25) extend the per-dependant step without changing the walk | Two walks whose closures overlap can deadlock and are retried by River; no tool yet adds evidence to an existing claim, so `LinkEvidence` is reached only from the store until FRB-57 exposes it through `contribute` |
| 2026-10-21 | `contribute` infers what it safely can before validating, in `internal/contribute` (domain validation stays strict): a generated ref (`<list>-<position>`) for any record without one; the evidence `source_kind` from well-known URIs only (Azure DevOps work items, Jira `/browse/KEY-1` on any host and GitHub issues are `ticket`; GitHub, GitLab and Bitbucket blob, tree and commit URLs and Azure DevOps `_git` URLs are `repository`; Confluence, SharePoint and Azure DevOps wiki pages are `document`; the command schemes are `command`, `person://` is `statement`; telemetry queries and other URLs are never inferred); `access_class` `area` when omitted; and `source_revision` only when a repository URL pins a full 40- or 64-hex commit SHA (in the path, or Azure DevOps `version=GC<sha>`, which the ticket's "SHA in the path" did not name but pins a commit as firmly). The request hash is taken after inference, so spelling out an inferred value is the same request. The tool's input schema requires only what cannot be inferred. The repository skill `.claude/skills/froodbase-contribute` teaches agents to structure contributions from plain language | A person should say what they learned and the agent should structure it (FRB-51); every inference rule must be one a reader would agree with from the URL alone, so a wrong guess never lands silently | A branch URL, a short SHA or an unrecognised link still needs its revision or kind, refused with a message saying what to pass. Defaulting `area` relies on the agent marking restricted sources, which the skill teaches. A retry of a call made before this change whose evidence had empty optional fields hashes differently and is refused as a different request |
| 2026-10-21 | Evidence for a claim already recorded is part of a `contribute` change set: `links: [{claim, evidence}]` names an existing assertion by id (never a ref in the same call) and cites evidence refs from the call or evidence ids in the area. The links are written in the contribution's transaction, after its evidence and before its new assertions, through the same path as `LinkEvidence` (claim evidence, `root_added` per distinct new root, re-projected score, `evidence_linked` audit naming the contribution, `reconsider_derived` when the claim has dependants); no revision is written and the claim is not added to `contribution_claims`, which lists the claims a contribution asserted. The result lists each linked claim under `linked` with its unchanged revision, the evidence linked, `roots_added` and its support. Evidence the claim already counts adds nothing and is not refused; an unknown claim, a claim or evidence in another area, or a link naming a ref is refused and nothing is written. A claim cites evidence only in its own area, for new assertions too (store `resolveEvidence` now refuses evidence in another area the caller can read) | Corroboration found later must strengthen the recorded claim rather than produce a duplicate that earns nothing (PR-15), and one transaction keeps the idempotent result, the new evidence and the links together (TR-15). Writing links first lets a deduction in the same call inherit the new roots directly | FRB-57. No migration. The skill teaches `links` (section "Adding evidence to something already recorded") and the MCP schema requires `claim` and `evidence` of each link |
| 2026-10-21 | Findings extracted from a document cite the document at a pinned version, one evidence record per section with the section heading as `locator`, and every section names one locator-less evidence record for the document as its `root`. The sections of one document at one version are one evidence root, so a deduction resting on two of its findings gains nothing from the second; a section that restates another source names that source as its root. A purely local file is never cited: findings cite what it relied on, and anything with nothing checkable behind it is listed back to the person, never stored | Two sections of one document are one author at one moment, not independent lines of evidence; counting them twice would let one document carry an inference past its threshold alone (PR-12, TR-25). Taught by the contribution skill (FRB-53); the server does not yet give sections of one document a shared root by itself | `.claude/skills/froodbase-contribute` section "Recording the findings in a document", development guide worked example, `TestDocumentFindings`; no schema or server change |
| 2026-10-21 | The slice 1b exit expects the inference derived from a ticket observation and an `az` command observation to meet the inference threshold, not to fall below it; the below-threshold case in the exit is a deduction resting on one document's findings | Under the service default configuration a ticket and a command run are two independent roots weighing 1 each, and the inference threshold is 2 (decision of 2026-10-21 on command and statement evidence). Expecting the inference below its threshold would mean weighting command runs down or treating independent sources as one root, which PR-12 forbids | `docs/planning/07-local-mvp.md` slice 1b exit reworded; `TestSlice1bExit` asserts two roots at write and three after the dreamer passes on a second work item (FRB-54) |
| 2026-10-21 | Scope overlap (TR-26, D3): every dimension must overlap. A blank or missing value is unspecified and matches anything; two specified names (environment, region, cluster, tenant) match when equal ignoring case and surrounding spaces. `version_min` and `version_max` are inclusive bounds, a missing one open; versions are an optional `v` then dot-separated whole numbers compared numerically, missing segments zero (2.4 = 2.4.0, 2.9 < 2.10). A bound that is not a version is treated as open when comparing, so it never rules out an overlap; `Scope.Validate` refuses it | One definition for the mode filter and the conflict classifier; an unreadable bound must not hide a record or a contradiction | The pitch's failure (prod, 2.3) and deployment (prod, 2.4) do not overlap: supersession is a declared correction (TR-33), not derived from overlap, and the slice 4 classifier will see them as a scope difference. `Scope.Validate` is not yet called on contribute (FRB-15 decides, at the input boundary and not on snapshot decode). The SQL function must normalise the same way |
| 2026-10-21 | Query modes as one predicate over lifecycle state and validity (TR-31, TR-34, TR-53): `current` keeps active and disputed records whose half-open validity `[valid_from, valid_to)` includes now, null bounds open; `as_of` keeps active, disputed and superseded records whose validity includes the as-of time, whenever they were recorded, and leaves out retracted ones; `historical` keeps everything. Every result carries a status relative to now: `current`, `historical` (superseded, retracted or valid only before now) or `upcoming` (in force, valid only from later). Recording time never enters the predicate | Superseding does not end validity unless an end date is asserted (TR-33), so the superseded failure is still what was valid on an earlier date; a retracted record was withdrawn and is not knowledge about any time; labelling a future-dated decision "historical" would mislead | A record with unknown validity passes every validity test and is labelled `validity_unknown`, never shown as verified. FRB-15's SQL function takes the reference time as an argument so the shared table runs deterministically |
| 2026-10-21 | Stale rule and freshness policy (TR-31, architecture design section 14): a record whose status is current is stale when its last check (`verified_at`, or `recorded_at` if never verified) is strictly older than its kind's maximum age; it is flagged, never excluded. The policy is per area in whole days by kind (absent or zero is no limit, a day is 24 hours); the default is 90 days for observations and inferences and none for decisions | An inference is no fresher than the world it was drawn from; a decision holds until someone changes it. Falling back to `recorded_at` stops a never-verified record from staying fresh for ever, and touches freshness only, never validity | `domain.FreshnessPolicy` and `DefaultFreshnessPolicy`; FRB-16 stores the per-area setting and its sweep must agree with `Classify` |
| 2026-10-21 | The temporal case tables live in `internal/domain/domaintest` as exported Go values (`OverlapCases`, `ModeCases`, `PitchRecords`), used by tests only | The domain tests and the store's SQL integration tests must answer to one truth (FRB-14, FRB-15); Go values keep the cases typed and reviewed in one place | `internal/domain`'s external tests may import its own helper packages (the boundary test allows it); a new case is checked by both implementations |
| 2026-10-21 | The temporal rules run in SQL as functions of migration 7 (`froodbase_scope_overlaps`, `froodbase_valid_at`, `froodbase_temporal_status`, `froodbase_in_mode`, `froodbase_stale`, `froodbase_freshness_policy`) that take the reference time as an argument; queries pass the service's clock. Every search channel filters by mode and scope inside its query, after row-level security and before the limit, and returns each hit's status and stale flag; `get_record` and `get_as_of` classify one record through the same functions | One definition per rule for every channel (D3, TR-53) that the shared case tables can check deterministically; filtering before the limit keeps a current search from being crowded out by superseded records | The store's integration tests run `domaintest.OverlapCases` and `ModeCases` through the functions; a rule change is a domain change, a case, and a migration that replaces the function |
| 2026-10-21 | `search` defaults to `current`; `as_of` needs an `as_of` time and an `as_of` time with any other mode is refused, as is a search scope whose versions are not versions. The identifier channel applies the mode to the matched name (the entity's lifecycle state with the name's validity), so an entity's former name is found only in `as_of` or `historical`, labelled with that name's status | TR-50 and TR-53 make current the question an investigation usually asks; a silently ignored time would answer a different question; names carry their own validity windows (TR-20) | An entity found by name carries that name's status; `get_record` labels an entity by its lifecycle state alone, since an entity has no validity of its own |
| 2026-10-21 | `get_as_of` evaluates the current revision of an assertion or entity at the asked time by validity time: valid when the `as_of` mode keeps it (an unknown validity is not ruled out; retracted never), an entity with only the names valid then. When it was not valid the result is `valid: false` with a reason and no record. Evidence is refused, having no validity of its own | TR-34: as-of asks what applied then by today's knowledge; `get_history` already answers what was recorded then. Returning an invalid record would invite an agent to use it | The tool output is `{id, as_of, valid, reason, record}`; reading a past revision by recording time stays with `get_history` |
| 2026-10-21 | Freshness policies are stored in the append-only `freshness_policy` table: the row with a null area is the service default (90 days for observations and inferences), an area's newest row replaces it whole, and a kind it leaves out has no limit. Rows are written through `store.PutFreshnessPolicy`; there is no tool to set one until curator tools arrive | Mirrors `support_config`: a curator setting with history, read under row-level security with the default visible to all | The dreamer's review sweep (FRB-16) reads the same policy through `froodbase_freshness_policy(area_id)`; changing a policy flags records, it never changes them |
| 2026-10-21 | A record contributed without dates is returned with status `current` and `validity_unknown: true` and no `verified_at`; tool descriptions say that current means "not known to have ended", not "verified current", and that stale records are flagged, not hidden. `contribute` checks scope versions and validity windows at its input boundary (stored scopes are not re-checked on read) and never fills a date in | PR-21, PR-22, TR-32: answers must distinguish unknown and unverified from verified current, and a scope that cannot be compared would match everything silently | Old rows with unreadable versions keep loading and count as open bounds; new ones are refused with the reason |
| 2026-10-21 | The review sweep's marks are projections in their own tables, never revisions or record columns: `review_flag` (one row per assertion a sweep has ever marked: `due_for_review`, and `stale_at`, when a sweep first found it stale, null while it is not) and `review_sweep` (per area: the last sweep's reference time and counts), both under area row-level security with select, insert and update grants only. The sweep computes stale with `froodbase_stale` under `froodbase_freshness_policy(area_id)`, the expression search and `ClassifyAssertion` use, and writes only rows whose flags changed; it never writes `assertion`, `revision`, `support_event` or `audit_event` | PR-33: age makes a record due for review and must not pollute its history or touch its state, validity or support. A separate table keeps the sweep from locking record rows writers update, and one SQL function keeps the live label and the sweep from disagreeing | FRB-16, migration `00008_review_sweep.sql`. `get_record`, `get_as_of` and `search` show `due_for_review`, `stale_at` and `review_swept_at`; the live `stale` can lead `stale_at` by one sweep. `list_due_for_review` (slice 3) reads the same tables |
| 2026-10-21 | A record is due for review when it is in force (active or disputed) and its `review_due_at` has come (`review_due_at <= now`); a record without a review date is never due, and validity plays no part. The rule is `domain.ModeRecord.DueForReview` and the SQL `froodbase_due_for_review`, both checked against `domaintest.DueCases` | A review date is a person's request to look again; a superseded or retracted record needs no review, and an ended validity is correct history whose review may still have been asked for.
