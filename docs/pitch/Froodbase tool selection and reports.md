# Build Froodbase around durable evidence

**For your requirements, I recommend a small shared Froodbase service built around PostgreSQL, with remote MCP access and versioned Markdown records.** Reuse the database, identity provider, MCP SDK and search components; own the narrow contract connecting investigations, reports, evidence and maintained knowledge. Your existing Azure platform makes that more attractive than it would be for a team starting without infrastructure. Hindsight remains a useful optional recall engine, not a prerequisite. Basic Memory Cloud is the closest packaged alternative if Markdown-first team knowledge meets your needs; Outline is stronger when a collaborative human knowledge-base interface matters most. This is a fit recommendation, not a benchmark result: no populated Froodbase or production investigation corpus was available.

## Reports and maintained knowledge need different lifecycles

An investigation should produce **two sibling outputs from the same evidence snapshot**. The Markdown report answers the user's actual questions: scope, findings, supporting evidence, rejected explanations, uncertainties and recommended actions. Its intended audience and purpose determine the structure; an incident report and an architecture review need not share a rigid template. Froodbase change set identifies reusable knowledge: verified observations, accepted decisions, diagnostic lessons, architecture corrections and proposed runbook changes.

A published report is an as-of deliverable. Give it a stable investigation/report ID, revision, publication time, environment and source references. Freeze each published revision; corrections create a new revision or addendum. Current knowledge evolves through review, validity dates and explicit supersession. Keep investigation completion, remediation completion and knowledge acceptance separate. The two outputs need different semantics, **not two databases**.

Store both in the shared remote service, or retain reports in an existing canonical document repository and reference exact revisions. Local Markdown downloads remain useful deliverables and working copies, but must not be the only shared record. Ingesting a report makes the case discoverable; it does not turn every hypothesis in it into accepted architecture. Conversely, a completed Froodbase update does not fulfil the obligation to deliver a report.

This distinction rules out using a continually regenerated summary as the report of record. Hindsight Knowledge Pages are query-generated Markdown views with background refresh behaviour. Their documentation also states that deletion is not detected by the page staleness check, so a page can appear current while citing a deleted fact. They are useful living summaries, not substitutes for issued investigation revisions. ([Knowledge Pages](https://hindsight.vectorize.io/developer/api/knowledge-pages))

## A narrow service fits better than another memory platform

The initial design can be **one Azure-hosted MCP/API service and Azure Database for PostgreSQL Flexible Server**. Reuse your existing Entra security groups: assign them Froodbase reader, contributor and reviewer app roles, scoped to the relevant knowledge where needed. Authenticate callers with Entra, enforce that mapping on requests and record the actual caller. The service can use managed identity and Entra-only database authentication; this avoids treating its pooled database identity as the human caller. Flexible Server supports pgvector. The infrastructure is conventional Azure; the remaining authorisation model is small and explicit. ([Entra app roles](https://learn.microsoft.com/en-us/entra/identity-platform/howto-add-app-roles-in-apps), [Entra database authentication](https://learn.microsoft.com/en-us/azure/postgresql/flexible-server/concepts-azure-ad-authentication), [pgvector support](https://learn.microsoft.com/azure/postgresql/extensions/how-to-use-pgvector), [Application authorisation](https://learn.microsoft.com/azure/app-service/configure-authentication-provider-aad))

Keep the domain model small: investigations; documents and immutable revisions; reusable claims; evidence references; and proposed or accepted knowledge changes. A document revision holds its exact Markdown body and metadata. A claim records its type, system/environment identity, epistemic state, evidence lineage, known validity interval, verification date and supersession link. Preserve design intent separately from observed deployment state. Shipped architecture enters as a versioned source with repository commit/path provenance, not an untraceable copy of live truth.

Expose explicit operations such as search, read an exact revision, publish a report, propose knowledge changes and accept or supersede a claim. Do not expose arbitrary SQL as the agent interface. Search should combine exact identifiers and PostgreSQL full-text retrieval with optional pgvector embeddings; return source passages and stable revision links. PostgreSQL already supplies indexed text search and ranking, so a separate vector database is unnecessary for the initial design. ([PostgreSQL text search](https://www.postgresql.org/docs/current/textsearch-intro.html), [pgvector](https://github.com/pgvector/pgvector))

**The real custom work is integrity, not embedding generation.** Enforce access before retrieval, reranking and model context assembly, and recheck source reads. Apply the same restrictions to caches, exports and derived summaries. PostgreSQL row-level security can reinforce this, but table owners and privileged roles can bypass policies; service roles must be deliberately configured. ([Row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html))

Require a base revision for edits, rejecting stale writers rather than silently overwriting. Use idempotency keys for publication and knowledge-change retries. Persist a durable indexing job alongside each committed change so an embedding failure leaves the report intact and indexing retryable. Report publication and Froodbase ingestion have independent statuses; “queued” is not “indexed.” Corrections and deletions must invalidate affected projections and identify derived claims requiring review.

Keep full text and vectors rebuildable from canonical records. Do not count a report, extracted memory and generated summary derived from one observation as three corroborating sources. Initially, explicit relationships in ordinary tables are enough; there is no need to build an automatic ontology, general wiki interface or autonomous consolidation engine. Backups, migrations, audit events and recovery remain operating responsibilities even when Azure handles the database infrastructure.

## Packaged alternatives remain credible choices

| Option | Where it fits | Why it is not the default here |
|---|---|---|
| **Basic Memory Cloud Teams** | Markdown-first shared knowledge, explicit observations/relations, native MCP | Closest buy option; domain-specific report publication and claim promotion still need discipline |
| **Outline** | Human collaboration, maintained reference pages, revisions and remote MCP | Database-backed documents with Markdown export; less natural for exact Markdown and claim-level semantics |
| **Hindsight** | Cross-investigation recall and synthesis of operational experience | Adds extraction/consolidation; does not own your report and review contract |
| **Graphiti** | Temporal dependency, ownership and relationship questions | Additional graph backend and entity-modelling burden |
| **Existing sources + Onyx** | Searching repositories, tickets and wikis without relocating them | Retrieval platform; authoring, report revisions and acceptance stay elsewhere |

Basic Memory's open-source engine treats Markdown as canonical and the database as an index. Cloud Teams adds shared projects, roles, versions and review features; cloud-only projects need no local synchronisation. Hybrid search already includes vectors. This is the first packaged product I would test against the custom proposal, but **do not assume self-hosting the OSS engine includes hosted Teams features**. Its documented broad workspace keys and ordinary-write concurrency behaviour need acceptance testing. ([Architecture](https://docs.basicmemory.com/reference/technical-information), [Teams](https://docs.basicmemory.com/teams/about), [Search](https://docs.basicmemory.com/concepts/semantic-search), [Keys](https://docs.basicmemory.com/cloud/api-keys))

Outline has remote MCP with OAuth, scoped API keys, collaborative editing and revision export. Its AI answers respect document access, but semantic AI features require cloud/licensed editions; parity between MCP search and that answer path was not established. Choose it when buying the human collaboration experience saves more work than enforcing custom records costs. Markdown export is not a promise of lossless round-trip editing. ([MCP](https://docs.getoutline.com/s/guide/doc/mcp-6j9jtENNKL), [API](https://docs.getoutline.com/s/guide/doc/api-1rEIXDfLF6), [AI answers](https://docs.getoutline.com/s/guide/doc/search-ai-answers-NIKPvYrx06), [Export](https://docs.getoutline.com/s/guide/doc/export-documents-svbz5EcJZu))

Of the memory engines, **Hindsight is my preferred optional addition for support experience**: it preserves documents/chunks alongside extracted memories and provides recall/synthesis. Prefer its service interface over copying a large extraction pipeline. Choose Graphiti only if temporal relationship questions demonstrate value beyond explicit relationships and hybrid search. Neither extraction mechanism establishes accepted truth. Mem0 offers memory operations but no decisive report-workflow advantage here; Letta's shared repositories are relevant, but its stateful-agent architecture introduces a larger runtime dependency. ([Hindsight documents](https://hindsight.vectorize.io/developer/api/documents), [Graphiti](https://github.com/getzep/graphiti), [Mem0](https://docs.mem0.ai/core-concepts/memory-operations/add), [Letta repositories](https://docs.letta.com/agent-sdk/repositories))

Onyx is attractive when authoritative material should remain distributed. Its remote MCP retrieves indexed knowledge, but source-permission synchronisation is an Enterprise feature. It does not remove report publication or knowledge-maintenance work. ([MCP](https://docs.onyx.app/overview/onyx_anywhere/mcp_server), [Connectors](https://docs.onyx.app/overview/core_features/connectors))

## Reuse components without inheriting an entire product

MIT is not the only permissive option, and hosted functionality is not automatically included with public source. These are the licences identified in the researched repositories; verify exact files and dependencies at pinned revisions before reuse.

| Component | Licence | Practical implication |
|---|---|---|
| [Hindsight](https://github.com/vectorize-io/hindsight/blob/main/LICENSE) | MIT | Permissive reuse with required notices |
| [Graphiti](https://github.com/getzep/graphiti/blob/main/LICENSE), [Mem0](https://github.com/mem0ai/mem0/blob/main/LICENSE), [Letta](https://github.com/letta-ai/letta/blob/main/LICENSE) | Apache-2.0 | Permissive, with applicable notice/modification obligations |
| [Basic Memory](https://github.com/basicmachines-co/basic-memory/blob/main/LICENSE) | AGPL-3.0 | Not an MIT code source; assess copyleft obligations |
| [Outline](https://github.com/outline/outline/blob/main/LICENSE) | Business Source License 1.1 | Current source is not permissively open-source |
| [Onyx](https://github.com/onyx-dot-app/onyx/blob/main/LICENSE) | MIT outside stated exclusions | Enterprise directories and third-party code have separate terms |
| [pgvector](https://github.com/pgvector/pgvector/blob/master/LICENSE) | PostgreSQL licence | Permissive; not MIT |

Reuse tested libraries and stable APIs before extracting algorithms. Independently implementing an idea differs from adapting source; calling an adaptation a rewrite does not automatically remove licence obligations. The valuable custom asset is the investigation-to-knowledge contract, not a new search engine.

Before committing further, evaluate exact-case lookup, analogous-incident recall, current versus superseded architecture, evidence citations, conflicting writers, access denial, correction propagation and report delivery while indexing is unavailable. **Build the narrow Azure service if these explicit record guarantees remain central; buy Basic Memory Cloud if it satisfies them with acceptable workflow conventions, or Outline if the human collaboration interface dominates.** Add Hindsight only when measured cross-case recall needs justify it. That keeps both the durable investigation output and the shared Froodbase useful without making either depend on an unnecessarily large memory platform.
