# Build a trustworthy Froodbase before indexing

**The repository has strong investigation and documentation practices, but it does not yet define a consistent lifecycle for “Froodbase.”** Its best instructions should produce useful, evidence-conscious individual workups; its weakest contracts concern authority, reuse, identity and keeping knowledge current. A vector or graph backend could improve discovery across those records, but would also make conflicting or weakly sourced claims easier to retrieve. Preserve authored Markdown and exact ticket state as authoritative records, repair the shared knowledge contract, then pilot one derived retrieval backend. Hindsight is the more natural first candidate for recurring support lessons; Graphiti is the stronger architectural fit when temporal relationships and change-impact questions dominate. This assessment reviews repository instructions and shipped architecture, with backend documentation checked on 13 October 2026. **No populated Froodbase or generated ticket corpus was available, and no runtime benchmark was performed:** expected output quality is inferred from instructions, while the document inconsistencies below were observed directly.

## Strong investigations do not yet form a coherent memory system

Froodbase is maintained by agents as well as skills. DevOps Ticket creates `<KEY>-<slug>/` workspaces containing `ticket.md`, `tasks.md`, `info.md` and `memory.md`. Support Agent uses `<KEY>/` with ticket, findings and memory files plus optional raw evidence. Architecture Change places five numbered phase documents beneath `tickets_dir/arch-<slug>/`. These layouts sensibly separate requests, findings, decisions and execution history. Support also explicitly resumes an existing local workup. ([DevOps layout](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-work-management/com.github.copilot/agents/devops-ticket.agent.md:100), [Support persistence](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-support/com.github.copilot/agents/support-agent.agent.md:75), [architecture workspace](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-infrastructure/com.github.copilot/agents/architecture-change.agent.md:61))

The three configured paths are only part of the knowledge estate. `system-map-discovery` reads packaged architecture and optionally compares an external knowledge checkout; `terraform-modules` participates in map maintenance. `doc-gen` writes documentation in the owning code repository, while TMF runbook authoring targets Confluence. That distribution is reasonable: implementation documentation belongs beside code, and case evidence belongs with the investigation. What is missing is a common statement of which destination owns each kind of fact and how findings graduate into maintained knowledge. ([Discovery](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-core/skills/system-map-discovery/SKILL.md:21), [module maintenance](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-infrastructure/skills/terraform-modules/SKILL.md:54), [documentation destination](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-core/skills/doc-gen/SKILL.md:14), [runbook destination](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-work-management/skills/tmf-runbook-authoring/SKILL.md:14))

Several authoring practices are particularly good. Support separates reporter wording from diagnosis, requires supporting and opposing evidence for hypotheses, preserves unknowns, and checks claimed mitigations against telemetry. Architecture discovery records facts with sources and distinguishes unavailable evidence from searches that found nothing. `doc-gen` goes further: it captures repository revision/state, distinguishes implementation evidence from illustrative material, and allows only verified candidates to establish factual architecture edges. These practices should produce substantially better material than undifferentiated conversation summaries. They should survive any backend migration. ([Support findings](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-support/com.github.copilot/agents/support-agent.agent.md:282), [causal discipline](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-support/com.github.copilot/agents/support-agent.agent.md:234), [discovery ledger](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-infrastructure/skills/architecture-change-design/references/discovery-ledger.md:9), [documentation evidence](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-core/skills/doc-gen/SKILL.md:26))

**The highest-priority defect is conflicting authority and maintenance policy.** Discovery treats the packaged map as the normal starting authority. DevOps and Support start with the external map, although the README calls that external checkout optional. DevOps instructs direct corrections and cites a self-updating AGENTS requirement absent from the current root instructions; Support proposes diffs without applying them. Consequently, the same discovery can receive different treatment depending on the entry point. Define one fallback, conflict-resolution and promotion policy before introducing automated reconciliation. ([Packaged authority](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-core/skills/system-map-discovery/SKILL.md:54), [optional external knowledge](/Users/robert/repos/AI.CloudToolkit/README.md:329), [DevOps maintenance](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-work-management/com.github.copilot/agents/devops-ticket.agent.md:145), [Support maintenance](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-support/com.github.copilot/agents/support-agent.agent.md:449), [root instructions](/Users/robert/repos/AI.CloudToolkit/AGENTS.md:1))

The next defect is **an incomplete reuse loop**. Support resumes the same ticket and supports named handoffs, but its similar-case search explicitly covers Jira and Confluence without searching other local `memory.md` or `info.md` records. Locally accumulated diagnostic reasoning therefore has no prescribed general discovery path. Add cross-ticket retrieval to the workflow even if the first implementation is exact-ID and keyword search using existing file tools. ([Same-ticket resume](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-support/com.github.copilot/agents/support-agent.agent.md:81), [similar-case search](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-support/com.github.copilot/agents/support-agent.agent.md:260))

Identity and status also need tightening. DevOps uses a summary-derived slug without Support’s explicit locate-and-resume step; duplicate workspaces after a summary change are a plausible risk, not an observed outcome. Architecture uses only a descriptive slug. More seriously, Support marks an investigation `done` before remediation, while DevOps uses `done` after implementation handoff. A future index must not interpret either as proof that the incident was resolved. Separate investigation status, authoritative ticket status and verified remediation outcome. ([DevOps scaffold](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-work-management/com.github.copilot/agents/devops-ticket.agent.md:105), [Support completion](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-support/com.github.copilot/agents/support-agent.agent.md:361), [DevOps completion](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-work-management/com.github.copilot/agents/devops-ticket.agent.md:238))

These are mostly consistency problems rather than poor writing. Some instructions are lengthy, and shared requirements are repeated unevenly; a concise common record contract would make compliance easier to inspect. There are also control inconsistencies worth separate human review: `doc-gen` declares T1 while describing T2 publication, and the packaged map’s cloning instruction conflicts with the higher safety contract’s approval requirement. This assessment proposes review, not control changes. ([Declared tier](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-core/skills/doc-gen/SKILL.md:9), [publication](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-core/skills/doc-gen/SKILL.md:765), [map instruction](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-core/skills/system-map-discovery/references/system_map.md:5), [safety contract](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-core/skills/operational-safety/SKILL.md:112))

## Shipped architecture is useful but unevenly traceable

The packaged architecture contains substantive operational knowledge. The map records ownership, repositories, dependencies and caveats; the Import Tool entry distinguishes a dated EU observation from an unverified US target. The Vision image lifecycle explains why the absence of a code commit does not prove there was no new image build, and distinguishes image selection in IaC from deployment through Ansible. Such explanations of causality and exceptions are valuable human knowledge that should remain readable regardless of storage technology. ([Import Tool](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-core/skills/system-map-discovery/references/system_map.md:17), [Vision lifecycle](/Users/robert/repos/AI.CloudToolkit/plugins/pxg-core/skills/system-map-discovery/references/architecture/phlexvision_vmss_image_lifecycle.md:67))

## Hindsight and Graphiti solve different retrieval problems

Neither product is merely a vector database. Hindsight combines fact extraction, memory retrieval and synthesis through `retain`, `recall` and `reflect`. Its normal PostgreSQL deployment already includes vector, keyword and graph mechanisms. Graphiti models entities and changing relationships, with episodes for provenance, temporal invalidation and hybrid retrieval over supported graph backends. Adding a separate vector service is therefore not a prerequisite for either. ([Hindsight overview](https://hindsight.vectorize.io/), [storage](https://hindsight.vectorize.io/developer/storage), [Graphiti overview](https://help.getzep.com/graphiti/getting-started/overview), [backend requirements](https://github.com/getzep/graphiti))

| Approach | Best fit here | Main tradeoff | Markdown relationship |
|---|---|---|---|
| Current files, improved contracts | Reviewable investigations, exact records, modest cross-case search | Discovery depends heavily on agent search discipline | Authored source remains directly readable |
| Markdown with hybrid search | Finding similar incidents and relevant passages | Retrieves conflicting versions unless metadata filters them | Original passages remain the retrieval evidence |
| Hindsight | Recurring support lessons and synthesized briefings | Extraction and consolidation introduce another interpretation layer | Original chunks plus generated Knowledge Pages |
| Graphiti | Dependencies, ownership and relationship changes over time | Entity resolution, ontology and graph operations require care | Retain authored documents separately and link episodes to them |

The fit assessments above are recommendations, not measured product rankings. Hindsight recall combines semantic, keyword, graph and temporal retrieval, with fusion and reranking. Its observation layer consolidates supporting memories; `reflect` synthesizes an answer with evidence references. This matches questions such as “What did we learn from similar callback failures?” It also documents fuzzy entity matching and possible erroneous merges: similarly named services and environments need explicit identity controls. ([Recall](https://hindsight.vectorize.io/developer/retrieval), [observations](https://hindsight.vectorize.io/developer/observations), [reflection](https://hindsight.vectorize.io/developer/reflect), [entity resolution](https://hindsight.vectorize.io/developer/retain))

**Hindsight now has human-readable Knowledge Pages**, including folder organization, refreshes, export and Markdown filesystem access. That narrows the gap between memory infrastructure and a browsable Froodbase. These are synthesized database-backed views, however; the documented interface does not establish lossless bidirectional synchronization of arbitrary existing Markdown, review history and formatting. Preserve authored architecture separately unless that round-trip requirement is explicitly tested. ([Knowledge Pages architecture](https://hindsight.vectorize.io/developer/knowledge-pages), [page API and exports](https://hindsight.vectorize.io/developer/api/knowledge-pages))

Graphiti better matches questions such as “Which services depended on this component when the incident occurred?” It supports reference-time episodes, custom entity/relationship types and changing facts. Its design separates validity time from system time, preserving historical relationships when facts are invalidated. That is useful for architecture history, but LLM extraction and contradiction resolution still require verification; a graph is not automatically a complete dependency inventory. Its search recipes also include configurable rerankers, so latency and cost should be measured for the chosen recipe. ([Episodes](https://help.getzep.com/graphiti/core-concepts/adding-episodes), [custom types](https://help.getzep.com/graphiti/core-concepts/custom-entity-and-edge-types), [author paper](https://arxiv.org/html/2501.13956v1), [search recipes](https://help.getzep.com/graphiti/working-with-data/searching))

Both add model calls, database operation, update processing and lifecycle responsibilities. Hindsight’s static API-key configuration is not inherently per-user isolation; Graphiti groups need application-enforced access rules. These boundaries matter if support records contain tenant-specific evidence. Retrieved prose must remain evidence, never new authorization to execute remembered commands. ([Hindsight extensions](https://hindsight.vectorize.io/developer/extensions), [Graphiti namespaces](https://help.getzep.com/graphiti/core-concepts/graph-namespacing))

## Establish authority, then test one derived backend

Keep authored architecture, decisions and runbooks in reviewable Markdown. Keep Jira authoritative for ticket fields, and local case folders authoritative for the investigation evidence they capture. Distinguish current implementation evidence from approved design intent: neither a recent observation nor an older decision automatically overrides the other. Treat embeddings, extracted facts, graphs and generated pages as **rebuildable projections returning canonical sources and revisions**. Do not ingest generated pages back as independent evidence; repetition of one claim is not independent corroboration.

Introduce a small shared metadata envelope: stable record ID and type, system/environment identities, source URI and revision, owner, recorded/observed times, verification state, review date and supersession links. Add validity dates where known rather than inventing them. Persist claim-level provenance for consequential assertions, drawing on `doc-gen` and the discovery ledger. Preserve hypotheses and rejected explanations in case history while promoting only reviewed findings into reusable architecture or runbooks. Define correction, deletion and re-indexing behavior alongside creation.

Then improve the existing workflows: use the same authority/fallback rule, locate existing records by stable ID before writing, retrieve relevant local cases explicitly, and validate required metadata and links. These changes address information quality and organization without requiring a new service. A graph or memory engine cannot supply the missing organizational decision about what counts as accepted knowledge.

Evaluate retrieval separately from authoring quality. First, use synthetic or appropriately selected cases to check whether the agents preserve evidence, unknowns, causal uncertainty and state distinctions. Then build roughly 30–50 adjudicated retrieval questions covering exact tickets, similar incidents, dependencies, historical state, contradictions and unsupported questions. Include identical service names in different environments, proposed versus approved changes, reopened tickets, duplicated summaries and late-arriving old evidence. No such test was executed for this assessment.

Compare the current workflow with Markdown hybrid search and one candidate backend using comparable evidence, answer models and context budgets. Judge correctness, citation accuracy, evidence recall, historical/current distinctions, false entity merges, abstention and update/deletion propagation. Also record searchability delay, latency, model cost and operator effort. Hold out questions and source revisions, and inspect failures manually. Vendor conversational-memory benchmarks cannot establish performance on these architecture and support tasks.

For support recall, pilot **Hindsight first**; for temporal architecture relationships, pilot **Graphiti first**. Retain a Markdown-only fallback throughout. Running both could eventually make sense for distinct, demonstrated workloads, but initially doubles extraction and synchronization surfaces without evidence of additional value. The practical decision is whether a backend improves trustworthy reuse enough to justify its operating cost; the repository already contains much of the valuable investigation discipline needed to make that experiment worthwhile.
