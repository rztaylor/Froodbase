# Reuse research: Graphiti and Hindsight

Status: research reference supporting the [architecture design](03-architecture-design.md) section 15 and the [implementation plan](04-implementation-plan.md). Froodbase is written in Go on PostgreSQL. Both projects are Python, so this research asks what *designs* to adapt, what to reject, and whether either is worth calling as a service. No code is copied from either.

Date: 14 October 2026.

The Graphiti paper ([arXiv 2501.13956](https://arxiv.org/abs/2501.13956)) describes Zep as of January 2025; the code has moved on, so the paper is design rationale, not current behaviour.

## 1. Headline conclusions

1. **Neither project is a service dependency for Froodbase.** Graphiti has no PostgreSQL backend and its maintainers closed the pgvector and Apache AGE requests as "not planned" ([#779](https://github.com/getzep/graphiti/issues/779), [#1095](https://github.com/getzep/graphiti/issues/1095)). Hindsight runs on PostgreSQL but its open-source auth is one shared API key mapped to one schema, with no per-user authorisation, and background jobs run with no caller identity ([extensions](https://hindsight.vectorize.io/developer/extensions)). Both auto-apply model decisions on the write path.
2. **Both validate Froodbase's core shape.** Graphiti's bitemporal edges and episode-as-provenance, and Hindsight's facts-plus-observations table with separate occurred, mentioned and created times, are the same split Froodbase already specifies. Froodbase adds what both lack: an explicit validity interval with its own provenance, a review state, and reversible entity merges.
3. **Four behaviours in each project directly violate Froodbase's rules** (section 4). They are design choices, not bugs, and they are why adaptation rather than adoption is right.
4. **The deterministic parts port cleanly to Go and SQL.** Entity-resolution tiers, hybrid retrieval with reciprocal rank fusion, interval-overlap conflict detection, delta-refreshed knowledge pages with watermarks, and citation validation in synthesis are all arithmetic or SQL.

## 2. Graphiti: what it does

**Data model** ([nodes.py](https://raw.githubusercontent.com/getzep/graphiti/main/graphiti_core/nodes.py), [edges.py](https://raw.githubusercontent.com/getzep/graphiti/main/graphiti_core/edges.py)). Every node and edge has `uuid`, `group_id` (namespace, required) and `created_at`. An `EpisodicNode` holds the raw source (`source`, `source_description`, `content`, `valid_at` which is the caller's reference time). An `EntityEdge` holds `name`, `fact` (a model-written sentence), `episodes[]` (every episode that asserted it), `reference_time`, and four temporal fields: `created_at` and `expired_at` (transaction time) and `valid_at` and `invalid_at` (world time, model-extracted). Nodes carry no world-time fields; only edges and episodes do. Communities are label-propagation clusters with model-written summaries of summaries.

**Provenance.** `Episodic -[MENTIONS]-> Entity` edges, `EntityEdge.episodes[]`, and `reference_time` copied from the originating episode. Re-asserting an existing fact appends the episode id to the edge.

**Contradiction handling** ([edge_operations.py](https://raw.githubusercontent.com/getzep/graphiti/main/graphiti_core/utils/maintenance/edge_operations.py), [dedupe_edges prompt](https://raw.githubusercontent.com/getzep/graphiti/main/graphiti_core/prompts/dedupe_edges.py)). For each new edge: hybrid search for duplicate and invalidation candidates (limit 10, unscoped), an exact fast path, then one model call returning `duplicate_facts` and `contradicted_facts`. The prompt is admirably conservative ("NEVER mark facts as contradicted unless the new fact explicitly makes the old fact false", "Do NOT infer contradiction from recency alone"). The *action* is not: flagged candidates get `invalid_at = new.valid_at` and `expired_at = now` with no review. If either side has no `valid_at`, nothing happens and the flag is silently dropped. Open issues show the failure modes: unscoped candidates retiring unrelated facts, with 3 of 4 audited retirements wrong ([#1728](https://github.com/getzep/graphiti/issues/1728)); the limit-10 window filling with dead facts ([#1956](https://github.com/getzep/graphiti/issues/1956)); negation leaving the original fact valid ([#1841](https://github.com/getzep/graphiti/issues/1841)).

**Dating.** The `extract_timestamps` prompt resolves relative dates against reference time and leaves both null when nothing is stated, which is good. It also says "If the fact is ongoing (present tense), set valid_at to REFERENCE TIME", and a regex pass clamps future-tense `valid_at` to reference time. Both infer validity from recording time.

**Entity resolution** ([node_operations.py](https://raw.githubusercontent.com/getzep/graphiti/main/graphiti_core/utils/maintenance/node_operations.py), [dedup_helpers.py](https://raw.githubusercontent.com/getzep/graphiti/main/graphiti_core/utils/maintenance/dedup_helpers.py)). A cascade: identity properties declared on the custom type, exact normalised name, MinHash over 3-gram shingles with Jaccard at or above 0.9 (gated by a name-entropy threshold so short names skip fuzzy matching), name-embedding cosine at or above 0.6 to gather up to 15 candidates, then a batched model call that may answer "new". A merge rewrites the uuid map; there is no un-merge. Zep's hosted docs state a policy of preferring under-merge to over-merge.

**Search** ([search_config.py](https://raw.githubusercontent.com/getzep/graphiti/main/graphiti_core/search/search_config.py), [recipes](https://raw.githubusercontent.com/getzep/graphiti/main/graphiti_core/search/search_config_recipes.py), [filters](https://raw.githubusercontent.com/getzep/graphiti/main/graphiti_core/search/search_filters.py)). Methods: cosine similarity, BM25 (backend full-text), breadth-first traversal to depth 3. Each fetches twice the limit, union, then rerank: reciprocal rank fusion, maximal marginal relevance, cross-encoder, node distance, or episode mentions. Sixteen named recipes. `SearchFilters` support date comparisons on all four temporal fields, so point-in-time is `valid_at <= T AND (invalid_at IS NULL OR invalid_at > T)`. Read-path methods other than the cross-encoder are deterministic; the whole write path is model-dependent.

**Storage and services.** Neo4j (a core dependency), FalkorDB, Kuzu (deprecated), Neptune. A FastAPI demo server and an experimental MCP server (`add_memory`, `search_memory_facts` with `center_node_uuid` and temporal filters, `build_communities`, and so on), Neo4j or FalkorDB only, no auth. Hosted Zep adds a proprietary graph engine, SDKs including Go, and governance.

## 3. Hindsight: what it does

**Data model** (Alembic chain under `hindsight-api-slim/hindsight_api/alembic/versions/`; the [storage page](https://hindsight.vectorize.io/developer/storage) deliberately publishes no DDL). One `memory_units` table holds facts and observations: `text`, `embedding VECTOR(384)` with HNSW, `fact_type` in `world`, `experience`, `observation`, `occurred_start` and `occurred_end` (when the event happened), `mentioned_at` (when it was stated), `created_at` (ingest), nullable `event_date` as a fallback (made nullable specifically so "no fabricated timestamp is recorded"), `tags[]`, `chunk_id`, and for observations `proof_count` and `source_memory_ids[]`. There is no validity interval. `entities` are unique per bank on lower-cased canonical name with a trigram index; `unit_entities` joins; `memory_links` are typed and weighted (`temporal`, `semantic`, `caused_by`). `documents` and `chunks` cascade-delete their memories. Invalidated units are *moved* to `invalidated_memory_units` so recall needs no state filter. `observation_history` and `mental_model_history` keep prior text. Knowledge pages are a folder tree over mental models.

**Retain** ([orchestrator](https://raw.githubusercontent.com/vectorize-io/hindsight/main/hindsight-api-slim/hindsight_api/engine/retain/orchestrator.py), [fact_extraction](https://raw.githubusercontent.com/vectorize-io/hindsight/main/hindsight-api-slim/hindsight_api/engine/retain/fact_extraction.py)). Regex screening, chunking at 3000 characters, model extraction into `what, when, where, who, why, fact_type, occurred_start, occurred_end, entities, causal_relations`, then deterministic entity resolution and link creation. The retain input's `event_date` "defaults to now" and is the reference for relative dates. The docs concede extraction is not fully deterministic.

**Entity resolution** ([entity_resolver.py](https://raw.githubusercontent.com/vectorize-io/hindsight/main/hindsight-api-slim/hindsight_api/engine/memories/pg/entity_resolver.py), no model). Trigram candidates at similarity 0.3 or above, a token-compatibility gate (mismatched numbers reject), then a score of 0.5 times string similarity plus 0.3 times co-occurrence with known neighbours plus 0.2 times temporal proximity, accepted at 0.6 or above. The code comments and the [retain docs](https://hindsight.vectorize.io/developer/retain) both document the false-merge risk: a short new name "can be absorbed" into an existing entity when it appears alongside that entity's associates. Merges are irreversible.

**Recall** ([retrieval docs](https://hindsight.vectorize.io/developer/retrieval), [fusion.py](https://raw.githubusercontent.com/vectorize-io/hindsight/main/hindsight-api-slim/hindsight_api/engine/search/fusion.py)). Four arms: semantic (pgvector cosine), keyword (`tsvector` with `ts_rank_cd`, which the docs admit is TF-IDF not BM25, with pluggable extensions), graph (single hop from semantic seeds, scored by shared entities and link weights), temporal (a local transformer builds a date window, then spreading over temporal and causal links). Fusion is reciprocal rank fusion with k of 60, then a cross-encoder reranks up to 300 candidates, then multiplicative boosts: recency (decaying over 365 days), temporal match, and `proof_count` for observations. No model in the loop beyond embedder, reranker and query analyser.

**Consolidation** ([consolidator](https://raw.githubusercontent.com/vectorize-io/hindsight/main/hindsight-api-slim/hindsight_api/engine/consolidation/consolidator.py), [prompts](https://raw.githubusercontent.com/vectorize-io/hindsight/main/hindsight-api-slim/hindsight_api/engine/consolidation/prompts.py)). Runs asynchronously after retain. Unconsolidated facts plus related observations go to a model that returns `creates`, `updates` and `deletes` with `source_fact_ids` and a reason. Actions citing no batch fact are discarded. The prompt tells the model to delete observations the new facts "directly supersede or contradict" and to update state changes in place. Near-duplicates merge at cosine 0.97 or above. Prior text goes to history. The live belief is machine-decided.

**Reflect** ([agent](https://raw.githubusercontent.com/vectorize-io/hindsight/main/hindsight-api-slim/hindsight_api/engine/reflect/agent.py), [docs](https://hindsight.vectorize.io/developer/reflect)). An agentic loop with forced tool order (mental models, observations, recall), disposition parameters (skepticism, literalism, empathy), and strict citation hygiene: identifiers only in arrays, an `available_ids` set, and `drop_unseen_ids` stripping anything the model did not see. Returns text plus `based_on` arrays.

**Knowledge pages** ([docs](https://hindsight.vectorize.io/developer/knowledge-pages), [API](https://hindsight.vectorize.io/developer/api/knowledge-pages)). Pages are built from observations only and never read other pages. First build is full, later refreshes are deltas with typed operations and untouched sections copied through byte-identical. A `last_memory_seen_at` watermark drives `is_stale`. Documented limitation, verbatim: "a page that cites a deleted fact keeps reporting itself up to date". Export is a Markdown bundle with front matter.

**API and auth.** Routes under `/v1/default/banks/{bank_id}/...` for retain, recall, reflect, memories, documents, entities, mental models, knowledge base, transfer and operations; MCP at `/mcp/{bank_id}/`. Open-source auth is off by default or one shared bearer key compared with plain `!=`. Per-user scoping exists only through custom extensions or tag scoping. The generated Go client targets API 0.4.11 and is stale against 1.0.

## 4. Behaviours that conflict with Froodbase's rules

| Froodbase rule | Graphiti | Hindsight |
|---|---|---|
| Never infer validity from recording time | "present tense means valid_at = reference time"; regex clamps future `valid_at` to reference time; episode `valid_at` is just the caller's reference time | Retain `event_date` defaults to now and anchors relative dates; recall's recency boost and temporal window fall back to `mentioned_at` |
| Never auto-resolve contradictions | Model verdict sets `invalid_at` and `expired_at` directly; paper: "consistently prioritizes new information"; issues #1728, #1956, #1841 | Consolidation prompt deletes or rewrites observations that are "superseded or contradicted"; dedup auto-merges at cosine 0.97 |
| Generated text is never accepted without review | `EntityEdge.fact`, entity summaries, community summaries and saga summaries are model-written and immediately searchable | Observations, mental models and knowledge pages are model-written and immediately served |
| Corroboration counts distinct evidence roots | `episode_mentions` reranker ranks by `len(edge.episodes)`, so every restatement raises rank | `proof_count` counts source memory units, which may all come from one chunk; it boosts recall |
| Permissions enforced per human caller before retrieval | `group_id` is a filter, and the docs say it "does not replace application authorization" | One shared key per schema; background jobs have no caller identity |

## 5. Reuse matrix

Adapt means re-implement the design in Go and SQL with the changes noted. Independent means Froodbase's own design already differs and should stay that way.

| Feature | Source | Verdict | Notes for Froodbase |
|---|---|---|---|
| Bitemporal fields on relationships (`created_at`/`expired_at` versus `valid_at`/`invalid_at`) | Graphiti | Adapt | Already in Froodbase as `recorded_at`, `valid_from`, `valid_to`. Add per-date provenance (who asserted the validity date and from what). Null means unknown, never reference time. |
| Episode as a provenance record linking to every claim it asserted | Graphiti | Adapt | Froodbase's contribution change set plays this role. Keep a `contribution_claims` join so a claim knows every contribution that asserted it, and keep the contribution's recording time separate from any validity date. |
| Separate `occurred`, `mentioned`, `created` times | Hindsight | Adapt | Same as Froodbase's model; Hindsight's own prompts insist on the separation. Froodbase adds `verified_at` and `review_due_at`. |
| Custom entity and relationship types as schema, with allowed (source type, target type) pairs | Graphiti | Adapt | Store relationship types in a table with allowed endpoint types and **predicate cardinality** (single-valued or multi-valued). Cardinality is what Graphiti lacks and what makes issue #1728 undecidable. |
| Conservative contradiction prompt rules | Graphiti | Adapt the rules, not the action | Reuse the prompt's rules verbatim in spirit ("explicit evidence of termination, replacement or mutually exclusive current state"; "never from recency"). The output becomes a dispute record, never an `invalid_at` write. |
| Deterministic interval-overlap check | Graphiti | Adapt as a detector only | Useful first pass in SQL. Never mutates the old record. Where either side is undated, surface an "undatable conflict" rather than silently doing nothing. |
| Date extraction: resolve relative dates against reference time; null when unstated; future plans do not start in the future | Graphiti, Hindsight | Adapt partially | Keep those rules. Reject "present tense means reference time". Extracted dates land as proposed with the evidence span that justified them. |
| Entity resolution cascade: identity keys, exact name, MinHash/Jaccard, embedding candidates, model last | Graphiti | Adapt deterministic tiers | Identity keys and exact names via unique indexes; trigram via `pg_trgm`; embeddings optional. The model tier, if used, produces a merge proposal for a curator. |
| Entity scoring: string similarity plus co-occurrence plus temporal proximity, accepted at 0.6 | Hindsight | Adapt as candidate scoring | Good for ranking merge candidates. Never auto-merge across environment scopes. Keep an alias table so merges are reversible. |
| Hybrid retrieval: full-text, cosine, graph expansion, union, reciprocal rank fusion with k of 60 | Both | Adapt | Already Froodbase's design. Hindsight's single-hop graph arm scored by shared entities and link weights is a cheap addition. Point-in-time filter is the Graphiti `SearchFilters` predicate as a SQL function. |
| Cross-encoder reranking | Both | Independent, optional | Model-dependent; keep out of the core ranking contract. Evaluate on the corpus later. |
| Episode-mentions reranker and `proof_count` boost | Graphiti, Hindsight | Independent | Replace with corroboration by distinct evidence roots. |
| Recency boost in ranking | Hindsight | Reject in current mode | Froodbase ranks by verification state and corroboration; recency of recording is not a signal. |
| Typed, weighted links between memories (`temporal`, `semantic`, `caused_by`) | Hindsight | Adapt selectively | Froodbase has derivation links and relationships. A `caused_by` link between assertions, proposed by a contributor and reviewed, is worth adding for lessons. Semantic links are a rebuildable projection and can wait. |
| Documents and chunks with cascade; re-retain replaces; delete removes derived memories | Hindsight | Adapt the bookkeeping, not the cascade | Report revisions are immutable in Froodbase. Deletion is redaction with a marker, and derived records are flagged for reconsideration rather than deleted. |
| Invalidation archive table | Hindsight | Independent | Froodbase keeps lifecycle state on the row plus revision snapshots; `current` mode filters by state. A separate archive is unnecessary. |
| Consolidation into observations with `source_memory_ids`, `consolidated_at`, history rows | Hindsight | Adapt bookkeeping, independent behaviour | Keep the watermark and source-id bookkeeping. The output is a proposed lesson, not a live rewrite; nothing is deleted. |
| Reflect: forced tool order, `available_ids`, `drop_unseen_ids`, `based_on` arrays | Hindsight | Adapt | Citation validation is exactly Froodbase's rule that a synthesis citing an unknown identifier is discarded. Disposition parameters are not needed. |
| Knowledge pages: folder tree, delta refresh, byte-identical untouched sections, watermark staleness, Markdown export with front matter | Hindsight | Adapt | For Froodbase's Markdown knowledge views. Fix the documented deletion gap: because Froodbase is append-only, a supersession or redaction is itself a write and moves the watermark. |
| Communities with summaries of summaries | Graphiti | Defer | Two model hops from evidence and auto-accepted. If clustering is wanted later, store summaries as proposed with member citations. |
| Model-written `fact` sentence and entity `summary` on every ingest | Graphiti | Independent | Froodbase stores the contributor's Markdown body as written, with the epistemic kind labelled. |
| Graphiti REST or MCP server | Graphiti | Do not use | Neo4j or FalkorDB only; no auth; demo grade. The `search_memory_facts(query, group_ids, center_node_uuid, valid_at, invalid_at)` shape is a reasonable minimal contract to mirror. |
| Hindsight as an optional service | Hindsight | Do not adopt | Shared-key auth, no per-user isolation, private and fast-changing schema (120 or more migrations in eight months), stale Go client, heavy Python and torch footprint. Usable as a development-time comparison oracle in the evaluation harness. |
| Hindsight bank export format (`manifest.json`, documents, per-table JSON) | Hindsight | Note only | The only stable interchange format if a comparison corpus is ever loaded into Hindsight. |

## 6. What could not be verified

- Graphiti: the paper PDF body (only the HTML rendering was read); whether hosted Zep shares the open-source invalidation code; the blog's claim that expired facts are rewritten to past tense (not found in current source); a possible parameter-name collision in `SearchFilters` with multiple OR groups (read, not tested); exact future-assertion regex patterns.
- Hindsight: the final `mental_models` DDL after the later migrations (fields inferred from API docs); the exact code assigning `event_date` and `mentioned_at` from an item timestamp; how the causal boost is applied in the graph arm; whether the `/v1/default/` segment can carry another tenant; reranking and boost code (formulas taken from docs); Hindsight Cloud pricing and whether per-user roles exist there.
