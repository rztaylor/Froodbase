# Changelog

All notable changes to Froodbase are recorded here. The format follows Keep a Changelog; versions follow SemVer once releases begin.

## Unreleased

### Added

- Slice 2 exit scenario: the pitch's version 2.3 to 2.4 story is a named acceptance test (PR-27). `TestSlice2Exit` in `internal/apitest` records, through the client `froodbase-mcp` uses, the failure reproduced in production on 2.3, the fix merged (repository scope), 2.4 deployed and verified, and the older investigation imported weeks later, with the dates and scopes of the shared domain case table. It shows that the current answer leaves out the superseded failure, an `as_of` question for the incident date returns it labelled historical, `historical` mode returns all four with labels, the merge leaves the failure active because its scope does not overlap production, and the late import adds a root to the failure without reopening it or making it current. Supersession is set directly on the state until slice 4's correction tool. A new guide, `docs/dev/guides/pitch-walkthrough.md`, linked from the development guide, tells the same story to Claude. No migration.
- The dreamer flags records that are due for review or stale (slice 2). A periodic review sweep, every hour by default (`FROODBASE_REVIEW_SWEEP_INTERVAL`, from `1m` to `24h`) and once at start, marks each area's records that are still in force and past their review date as `due_for_review`, and records not checked within their area's freshness policy with `stale_at`, the time a sweep first found them stale. The marks sit beside the records: a sweep never changes a record's state, validity, support or revisions, and age never removes anything. `get_record`, `get_as_of` and `search` show `due_for_review`, `stale_at` and `review_swept_at`; the live `stale` flag is unchanged and can lead `stale_at` by one sweep. `froodbase-dreamer review-sweep` runs a sweep now. Migration `00008_review_sweep.sql` adds the `review_flag` and `review_sweep` tables with row-level security and the due-for-review rule as an SQL function checked against the domain's case table.
- Claude can ask what is true now, what was true then, or everything (slice 2). `search` takes `mode`: `current` (the default) keeps what is in force and valid now; `as_of` with an `as_of` time keeps what was valid then by when it applied, so a record imported later about an earlier time is found and a superseded one is kept, labelled; `historical` keeps everything. An optional `scope` keeps records whose scope overlaps it. Every result is labelled `status` current, historical or upcoming relative to now, and a current record not checked within its area's freshness policy carries `stale: true` and is still returned. The new `get_as_of` tool reads one assertion or entity as valid at a time, or says why it was not. A record contributed without dates is marked `validity_unknown` and is never shown as verified. `contribute` refuses scope versions it cannot compare and validity that ends before it starts. Searching for an entity's former name now finds it only in `as_of` or `historical` mode. Migration `00007_temporal_queries.sql` adds the rules as SQL functions checked against the domain's case tables, the per-area `freshness_policy` table with the 90-day default and a validity index on entity names. The contribute skill and the development guide show giving dates and scope, and asking in each mode.
- The rules for the two clocks, in `internal/domain` with table-driven tests and no storage yet (slice 2). A record's validity stays separate from when it was recorded. Scope has six fixed keys, and two scopes overlap when every key does; version ranges are compared numerically. Each query mode is one predicate. `current` keeps active and disputed records valid now. `as_of` keeps what was valid at a time, whenever it was recorded, superseded records included and retracted ones left out. `historical` keeps everything. Every record is labelled current, historical or upcoming relative to now, and a current record not checked within its area's freshness policy is flagged stale, never hidden. The default policy is 90 days for observations and inferences and no limit for decisions. The pitch's version 2.3 to 2.4 records are part of a shared case table (`internal/domain/domaintest`) that the SQL storage will be checked against. Nothing changes for callers yet.
- Slice 1b exit scenario: `TestSlice1bExit` in `internal/apitest` drives the whole slice through the client `froodbase-mcp` uses: a plain-language finding from a work item, an observation from an `az` command, an inference derived from both, the person's own statement, a second work item added under `links` that the dreamer passes on to the inference, the sample document's findings citing their sections, and every record read back with its sources through `get_record`, `get_history` and `search`. The development guide's walkthrough gains a command-observed fact (step 13) and a deduction from it read back with its sources (step 14). The slice 1b exit in the local MVP plan now expects that inference to meet its threshold, since a ticket and a command run are two independent roots.
- Claude can record the findings in a document without sending it: asked to record what is useful in a document, it reads it with its own tools and contributes each finding (observations, inferences derived from what they rest on, decisions) citing the document at a commit with the section as locator, in one change set. The document is recorded once as the root of every section cited, so it counts as one source however many of its findings are cited. A local file is never a citation: Claude cites what it relied on, records the person's own knowledge only with their agreement, and lists what it could not store. The skill section, a sample document in `docs/dev/guides/sample-design-note.md`, a worked example in the development guide and `TestDocumentFindings` cover it.
- New evidence can be added to something already recorded without recording it again: `contribute` takes `links`, each naming a recorded claim by id and the evidence it should now cite (new evidence in the same call or evidence the area holds). The claim gains one root per independent source it did not count yet and keeps its revision; deductions derived from it gain the root through the dreamer. Evidence it already counts adds nothing; an unknown claim, or a claim or evidence in another area, is refused and nothing is written. The result lists each linked claim under `linked` with `roots_added` and its support, and a retry with the same key replays it. The contribute skill and the development guide's walkthrough show it. Citing an existing evidence id from another area you can read is now refused for new claims too. No migration.
- A person can say what they learned in plain words and Claude records it: the repository skill `.claude/skills/froodbase-contribute` teaches Claude to search before creating, cite existing records by id, choose the assertion and evidence kinds, record deductions derived from what it read and commands it ran as command evidence, keep secrets out, mint the idempotency key and report the ids it wrote, asking the person only when a claim has nothing checkable behind it. `contribute` now fills in what it can tell: refs for records nothing refers to (`entity-1`, `evidence-2`, ...), the evidence kind of well-known links (work items, Jira and GitHub issues as tickets; GitHub, GitLab, Bitbucket and Azure DevOps repository URLs as repositories; Confluence, SharePoint and Azure DevOps wiki pages as documents; the command and person schemes), the `area` access class, and the revision of a repository URL that pins a full commit SHA. Anything it cannot tell is still required and refused with a message saying what to pass; the tool's input schema no longer lists the inferred fields as required. The development guide's walkthrough is rewritten so the person speaks plainly.
- Deductions grow stronger when their sources do. When a record that something was derived from gains a new evidence root, the dreamer's `reconsider_derived` job (enqueued in the same transaction, unique per record while it waits) walks every record derived from it, directly or through other deductions, and appends the root to each one that has not already counted it, directly, through another source or as the same person's statement. The new `root_added` events name the job (`job_name: reconsider_derived`) and the source they were inherited from, scores are re-projected under the area's current configuration, and no revision is written; `get_record` and `get_history` show the result. The walk stays in the record's area and stops on cycles. The dreamer's health endpoint reports `reconsider_waiting`. No migration.
- Facts found by running a command, and things a named person knows, count as evidence. A `command` citation names what was observed (an Azure resource id as `azure:///subscriptions/...`, a Kubernetes object as `k8s://<cluster>/<namespace>/<kind>/<name>`, a database as `sql://<server>/<database>`, or `host://<name>`), the exact command or query with secrets removed as its `locator`, when it ran as `observed_at` and optionally the output relied on as `excerpt`; running it again later is a second root. A `statement` citation records what the caller said, `person://<their user id>` (filled in when left out), with the statement as its `excerpt` and when they said it; citing someone else's statement, or recording one with no person behind the call, is refused, and one person's statements count once per claim. A statement root weighs 0.5 by default under the area's support configuration (`root_weight_by_source_kind`; observed sources weigh 1), so a statement alone stays below an observation's threshold; support in `contribute` results and `get_record` shows `roots_by_source_kind` with each kind's weight. Evidence whose URI, command or excerpt looks like a secret (a connection-string or URL password, a bearer token, a key or token value, a private key) is refused with a message naming the kind of secret, never the value. Migration `00006_command_statement_evidence.sql` adds the kinds, the per-root source kind on support events and the root weights; no existing score changes.
- Agents can record deductions: `contribute` takes an `assertions` list whose entries have a `kind` (observation, decision or inference). A decision or inference may cite evidence, name in `derived_from` the assertions it was concluded from (refs in the same call or ids in the area), or both; an observation still cites evidence and is never derived. A deduction is active at once, stays labelled with its kind, and starts with one `root_added` support event per distinct evidence root of its sources and its own citations, each inherited one naming its sources; a root shared by several sources counts once. Deriving from another area, an unknown id or in a loop is refused and nothing is written. `get_record` and `search` show `derived` and `derived_from`, `get_history` shows the `derivations`, and an inference below its area's threshold is still returned with `meets_threshold: false`. Migration `00005_derivation.sql` adds the append-only `derivation` table with row-level security. The `observations` list keeps working as assertions of kind observation.
- Slice 1 exit scenario: `internal/apitest` starts froodbase-api in-process on a disposable database with a working dreamer, and `TestSlice1Exit` drives contribute, replay, search by name, near-miss and body word, get_record, get_history, a refused reader, a stranger seeing nothing and the index job through the client `froodbase-mcp` uses. The development guide has a five-minute walkthrough in Claude.
- The dreamer keeps search projections current: every entity or assertion write enqueues an `index_record` job (unique per record while it waits or runs) that records the indexed revision in `index_state`; `froodbase-dreamer rebuild-index <area-id>` re-indexes an area; the dreamer's health endpoint reports `index_total` and `index_stale`.
- `search` tool: finds entities by exact or near-miss name (trigram similarity, near-misses labelled as candidates) and observations by words in their body, over the caller's knowledge areas only, with every result carrying kind, lifecycle state, support, scope, validity, verification date, citations and the channel that matched. Reads of restricted evidence are audited.
- `contribute`, `get_record` and `get_history` tools in `froodbase-api` and through `froodbase-mcp`: a contributor writes an atomic change set of entities, observations and evidence to a knowledge area and gets back every record's id, kind, lifecycle state (active) and support; retries with the same idempotency key replay the stored result; a reader's attempt is refused and audited; any record is readable by id with its support and citations and its append-only history. Knowledge areas are created at API start-up for the keys the users file grants.
- Records are stored with full history, audit and per-area access control: migration `00002_records.sql` creates the slice 1 tables (knowledge areas, entities and names, observation assertions, evidence citing living sources by URI, revision and locator, claim evidence, contributions, revisions with full snapshots, audit events, support events and versioned support configuration seeded with the service default), with row-level security on every table keyed on the caller's areas and a non-owning service role, `froodbase_app`, that cannot bypass it. A transactional writer in `internal/store` records each write with its revision, audit event, one `root_added` support event per distinct evidence root and the `index_record` job together; the support score is a recomputable projection of a claim's events under the area's configuration version. Queries are generated with sqlc (`make sqlc`).
- The local stack now runs the api and dreamer as `froodbase_app` with its own generated password (`FROODBASE_APP_DB_PASSWORD`); a database volume created before this change needs either `docker compose down -v` or the one-line `ALTER ROLE` in `docs/dev/ops/development.md`. `froodbase-api migrate` now applies River's schema before the goose migrations.

### Changed

- The contribution skill cites a file from a local git checkout only as a version others can open: the file has no uncommitted changes, it is cited at the last commit that changed it, that commit is on the shared remote (the upstream when `origin` is a personal fork), and the repository is open to the knowledge area's readers. Otherwise Claude treats it as a local file or asks the person to commit and push. The skill also gives the permalink form for GitHub, GitLab, Bitbucket and Azure DevOps remotes, without any credentials the remote address carries.
- Planning (docs only): the local MVP gains slice 1b, so agents can record deductions linked to their sources, cite facts from commands and statements by named people, and contribute from plain language or a document, and slice 3b, which imports the system-map-discovery architecture references and regenerates them as readable views so Froodbase can take over from those files.
- Evidence and contributions belong to a knowledge area, and evidence can name a locator (line range or section) inside the cited revision.

- Evidence can no longer cite a report revision held by Froodbase: the `report_revision` source kind and `froodbase://` URIs are removed from the knowledge model, leaving repository, ticket, telemetry query and document sources, each naming its revision.
- Planning direction (docs only, no shipped behaviour yet): a claim's certainty is now an earned support score rather than a proposed-to-accepted approval step. Support rises with distinct evidence roots, verification checks and evidenced use outcomes reported through a new `report_outcome` tool, and falls on contradiction, failed outcomes, source changes and reviewer flags; retrieval and repetition add nothing. The lifecycle is active, disputed, superseded, retracted. Reports, conversations and transcripts are never an input: the planned `ingest_report` tool, its local preview, source-copy retention and the `report_revision` source kind are removed from the design, and `propose_contribution` is renamed `contribute`.

### Fixed

- Image builds no longer depend on fetching the Dockerfile syntax frontend from Docker Hub, which timed out on some networks; Docker's built-in BuildKit frontend supports the cache mounts the Dockerfile uses.
- Building or testing on a Mac without Xcode's Command Line Tools no longer triggers Apple's developer-tools prompt: binaries build with cgo disabled everywhere, and on macOS the tests do too.

### Added

- The knowledge model exists as code (`internal/domain`, no database or network): knowledge areas, entities whose identity survives renames, observations, evidence and contributions. Evidence must cite a source the audience can open: local file paths and URLs on the contributor's machine are rejected, only the five documented source kinds are accepted, every citation names its revision, and an evidence record may never be shared more widely than its source. Corroboration counts distinct evidence roots, so a report, an excerpt and a summary of it count once. Creating an observation never copies its recording time into its validity dates.
- `make test-integration` runs the integration tests against a disposable PostgreSQL started by Testcontainers (`internal/store/storetest` gives each test its own migrated database); CI runs them in a separate job and the unit gate stays Docker-free.
- `froodbase-dreamer` runs background jobs with River against the local database: a heartbeat job every minute, scheduled only by the elected leader and unique per minute, and a health endpoint (`FROODBASE_DREAMER_ADDR`, default :8081) reporting queue depth. `froodbase-api migrate` now also applies River's job queue schema, and the Compose stack applies migrations through a one-shot `migrate` service before the api and dreamer start. `internal/store` can enqueue jobs inside a transaction.
- `froodbase-mcp` is a stdio MCP server for Claude Code: it forwards tools to `froodbase-api` with the person's credentials from `FROODBASE_API_URL`, `FROODBASE_USERNAME` and `FROODBASE_PASSWORD`, returns a structured `froodbase_unavailable` result instead of an error when the API cannot be reached, and sends its version on every call; `froodbase-api` publishes `min_client_version` on `/healthz` and warns about older clients.
- Basic auth for the local API: `froodbase-api` loads a static users file (`FROODBASE_USERS_FILE`, bcrypt hashes only) and serves MCP over Streamable HTTP at `/mcp` behind HTTP basic auth, with a `whoami` tool reporting the caller's identity and (area, role) grants. `froodbase-api hash-password` creates a hash from stdin; `make up` creates `local/users.json` with three sample users.
- Versioned schema migrations with goose, embedded in `froodbase-api`: `froodbase-api migrate` applies them and `froodbase-api migrate --status` lists them; `make migrate` and `make migrate-status` run them against the Compose database. The first migration enables pgvector, pg_trgm and btree_gist. `internal/store` owns the PostgreSQL pool, which both server binaries open at startup.
- Local stack in Docker Compose (`make up`, `make down`, `make logs`): PostgreSQL 16 with pgvector, `froodbase-api` and `froodbase-dreamer` built from the root `Dockerfile`; `.env.example` documents every `FROODBASE_` variable and `make up` generates the local database password into the ignored `.env`. `froodbase-api` answers `GET /healthz`; `froodbase-dreamer` logs a startup line. `internal/config` loads the `FROODBASE_` variables; a CI job builds the images, starts the stack and checks health.
- Repository foundation: Go module with the `froodbase-mcp`, `froodbase-api` and `froodbase-dreamer` entrypoints, shared `internal/version`, lint and validation gate, CI workflow, Dependabot, repo-local facts and developer docs.
- Planning documents moved from the AI.CloudToolkit reports folder and renamed to Froodbase.
- Local MVP scope (`docs/planning/07-local-mvp.md`): the brain built first in Docker Compose with basic auth, as six slices; decisions on Compose, basic auth behind the authorisation-context interface, goose and Testcontainers recorded.
